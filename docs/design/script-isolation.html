技能脚本进程隔离

范围 src/no_agent/skills/runtime.py、compose.py、tools/base.py 前置 沙箱止血补丁（模块代理、block 模式、权限委托）

结论：把技能脚本的执行从宿主进程移到一次性的子进程（worker）。工具、LLM、子技能调用、权限检查、密钥全部留在宿主，worker 只能通过一条 JSON 管道请求宿主代办。步骤循环和计时由宿主驱动，超时直接杀掉 worker。

  • 新增配置 script_isolation：inprocess / process（默认）/ sandbox。
  • process 解决三件事：逃逸后拿不到宿主对象和密钥；死循环能被打断；资源有上限。它不阻止读本机文件和联网。
  • sandbox 在此之上加操作系统级约束（Linux 上的 Landlock / seccomp），不可用时拒绝启动，不静默降级。untrusted_shared="shadow" 只在这一档下允许。
  • 现有的 AST 白名单和模块代理保留，作为纵深防御的内层。

问题

止血补丁封住了已知的逃逸手法，并且默认不执行不可信的共享技能。但脚本仍然和框架在同一个进程里运行，有三个问题补丁解决不了：

  1. 逃逸即接管。白名单只能封已知手法。任何一个新的绕过都能拿到 Toolbox、AgentConfig（含 LLM API Key）和真实 builtins，所有权限检查随之失效。
  2. 可用性。while True: pass 或同步 time.sleep 会卡住整个事件循环。_run_step 的超时依赖事件循环调度，此时完全失效，HTTP 服务和 MCP 服务一起挂起。这不需要恶意，LLM 写错一次就会发生。
  3. 信任只能二选一。不可信技能要么完全不跑（block），要么在宿主进程里跑（shadow）。没有"在笼子里试跑"的中间选项。

威胁模型

假设攻击者能让任意 Python 代码出现在技能脚本里。脚本的来源有三条：

来源怎样变成恶意代码止血补丁后的状态
共享仓库 / extra_skill_dirs仓库被投毒，或签名者私钥泄露未签名默认不执行；已签名直接信任
LLM 修补 / 提炼接管时 AI 读到网页或工具输出里的提示注入，把恶意代码写进"修补"，经回归测试后自动上线直接执行，没有任何隔离
框架内置供应链攻击（不在本提案范围）信任

要保护的资产，按严重程度排列：宿主内存和环境变量里的密钥；技能未声明的工具和域名；本机文件；网络；服务可用性；其他技能的运行状态。

目标与非目标

目标

  • 脚本即使完全逃逸 Python 层沙箱，也拿不到宿主对象和密钥，也绕不过工具 / 域名权限。
  • 任何脚本都能在超时后被可靠终止，内存和 CPU 有上限。
  • ctx API 对脚本作者不变，现有技能无需修改。
  • 热路径（命中技能直接执行）的额外延迟控制在个位数毫秒（预热池命中时）。
  • 支持 Python 3.10+，不引入必选依赖。

非目标

  • 防御内核漏洞或 Python 解释器本身的内存安全漏洞。需要这一级时，用容器或虚拟机部署。
  • 第一期在 Windows 和 macOS 上提供文件系统 / 网络隔离（见平台差异）。
  • 隔离 AI 自由执行（freeform）。它本来就只能通过工具行动，不执行任意代码。

方案

宿主进程（可信）

  • 编排：步骤循环、计时、超时击杀、StepRecord
  • 静态解析：步骤名、idempotent、kind、guard / verify
  • Toolbox：权限检查、确认、录制、ReplayToolbox
  • LLM 客户端和 API Key
  • SkillCaller：子技能开新 worker
  • 预算：工具和 LLM 调用次数

worker 子进程（不可信）

  • 加载脚本（AST 白名单 + 模块代理照旧）
  • 持有 ctx.state、ctx.result
  • 按宿主指令执行单个阶段：guard / 某一步 / verify
  • ctx.tool / llm / ask / skill 是 RPC 桩
  • 只有标准库，空环境变量，空临时目录
sequenceDiagram
    participant H as 宿主
    participant W as worker（一次性）
    H->>W: load(source, task, params)
    W-->>H: loaded
    loop 每个阶段：guard → 步骤 1..n → verify
        H->>W: run(phase, name)
        W->>H: call(tool, "fetch_page", args)
        Note over H: 权限检查 → 确认 → 执行 → 录制
        H-->>W: reply(ok, value)
        W-->>H: done(ret, state 快照, logs)
    end
    Note over H: 超时：SIGKILL / TerminateJobObject，用上一个快照
    H->>W: close（进程退出，不复用）

关键决定

  1. 宿主驱动步骤循环。worker 一次只执行宿主指定的一个阶段。计时、超时、失败归因都在宿主，worker 无法伪造"已完成"或拖延计时。等待用户输入的时间由宿主计算（它自己在处理 ask_user），扣除逻辑和现在一致。
  2. 步骤元数据以宿主静态解析为准。宿主用 validate_script 和 AST 得到步骤列表与 idempotent 标记，worker 的上报只用于核对，不一致即判加载失败。
  3. worker 用一次就丢。一个 worker 只服务一次脚本执行，结束即退出，防止恶意代码在进程里驻留，污染下一次运行。启动成本由预热池吸收：池里是已经启动、但还没加载任何脚本的空 worker。
  4. 只用 spawn，禁止 fork。fork 会把宿主内存（含 API Key、Toolbox 对象）原样复制进子进程，隔离就没有意义了。worker 用 python -I <worker.py 绝对路径> 启动，环境变量只保留运行所需的最小集合（PATH、SYSTEMROOT 等）。
  5. worker 不 import no_agent 包。no_agent/__init__.py 会拉进 pydantic、openai、sqlmodel，既拖慢启动又扩大攻击面。worker 是一个只依赖标准库的独立文件，脚本沙箱代码（白名单、模块代理）从 script.py 抽到一个纯标准库模块，宿主和 worker 共用。
  6. 只用 JSON，永不 pickle。宿主反序列化 worker 发来的 pickle，等于让 worker 在宿主里执行代码。所以协议只用带长度前缀的 JSON 帧，单帧上限 8 MiB，宿主按协议校验每条消息，畸形或超限即杀掉 worker。
  7. state 每个阶段快照。每个阶段结束时（成功或失败），worker 都回传 to_jsonable 并截断后的 state 快照，所以脚本失败时的快照与进程内执行完全一致。只有 worker 因超时被杀时，接管上下文用的是上一个阶段的快照，看不到被终止的步骤里改了一半的 state。
  8. 每个 ctx.skill 开一个新 worker。父子技能如果共用一个进程，低权限的子技能可以篡改父技能的函数，借父技能的权限调用工具。分开进程后，权限委托（子技能用自己声明的权限，未声明的部分继承调用方）在宿主执行，和当前语义一致。嵌套深度上限 MAX_DEPTH = 3 保持不变，同一时刻最多存活 4 个 worker。
  9. 每次执行有预算。工具调用次数、LLM 调用次数、累计输出字节数各有上限，超限按步骤失败处理，防止脚本刷爆 LLM 费用。

协议

协议帧走 worker 的 stdin / stdout，格式为 4 字节大端长度加 UTF-8 JSON。worker 在加载脚本之前把 sys.stdout 换成 stderr，所以脚本里的 print 不会混进协议，宿主把 stderr 当日志收集。

实现时与草案的差异：草案计划另开一对管道。改用 stdin / stdout 是因为 Windows 上向子进程传递额外的管道句柄很麻烦，而且已经逃逸的代码不论协议走哪条管道都能伪造帧，另开管道并不能多挡住什么。宿主对每一帧做格式校验，畸形即终止 worker。

方向op字段说明
宿主 → Wloadsource, task, paramsworker 执行静态校验和加载，回 loaded（步骤名列表）或 failed
宿主 → Wrunphase: guard | step | verify, name执行一个阶段；guard 阶段的只读限制由宿主在处理 call 时检查
W → 宿主callid, kind: tool | llm | skill, name, argsctx 方法的 RPC，ask / confirm 走 tool: ask_user
宿主 → Wreplyid, ok, value | error{kind, message}kind：tool_error、permission、abort、budget、llm_error。worker 把它转成 ToolError / StepFailure / UserAbort

用户取消时，宿主收到 UserAbort 后不必等 worker 收尾：直接记为 aborted，然后杀掉 worker。

隔离级别

每一档能挡住什么，以"脚本已完全逃逸 Python 层沙箱"为前提：

脚本能否……inprocessprocesssandbox（Linux）
读到 API Key / 宿主内存能不能不能
绕过工具 / 域名权限能不能不能
篡改其他技能的状态能不能不能
卡死服务（死循环）能不能不能
耗尽内存能受限*不能
启动子进程能受限*不能
读写本机文件（当前用户权限内）能能不能
直接联网能能不能

* Linux / macOS 用 setrlimit（RLIMIT_AS、RLIMIT_CPU、RLIMIT_NPROC），Windows 用 Job Object（进程内存上限、活动进程数为 1、句柄关闭即终止）。

默认取 process：脚本最常见的来源是 LLM 修补，这一档对任何平台都有效，代价只是几毫秒延迟。inprocess 留给单元测试和明确信任所有脚本的场景；选择它时启动日志给出警告。

对现有功能的影响

功能变化
回归测试 run_tests现在用 asyncio.gather 并发执行所有用例。改为用信号量限制并发 worker 数（默认 CPU 核数），否则一次提炼会瞬间拉起几十个进程
ReplayToolbox不变，它在宿主侧

guard 只读检查从 StepContext.tool 移到宿主的 CtxBridge，未注册的工具一律拒绝（现在会放行）
verify作为一个阶段运行，获得和步骤相同的超时（现在没有超时）
AI 接管TakeoverContext.state 改用最后一个成功阶段的快照，见关键决定第 7 条
浏览器工具不变。Playwright 会话留在宿主，脚本照旧通过 ctx.tool 操作
Python 层沙箱保留在 worker 里，作为内层防线；错误提示照旧给 LLM 修补时参考

被否决的方案

方案否决理由
继续加固进程内沙箱打地鼠。止血补丁的过程中又发现了 match 类模式、string.Formatter 两种新的绕过，而且这条路永远解决不了死循环
RestrictedPython本质相同（编译期改写 + 运行时守卫），仍在宿主进程内，且多一个依赖
子解释器（PEP 734）需要 3.12+ / 3.14，项目要求 3.10+；同进程共享地址空间，官方明确它不是安全边界
WASM（Pyodide、wasmtime + CPython.wasm）隔离最强，但依赖重、冷启动慢，异步 RPC 桥接复杂，标准库兼容性要逐个验证。可以作为将来 sandbox 档的跨平台后端
每次运行起一个容器需要 Docker 守护进程，延迟在秒级，违背"脚本是最快路径"的定位。可以作为服务端部署的可选 Runner
复用 worker（不用一次就丢）恶意代码可以驻留在进程里，篡改下一次运行。预热池已经能吸收启动成本，复用省下的时间不值这个风险

反方审查

对本提案最有力的反对意见：

本地技能都是我们自己的 LLM 写的，止血补丁之后不可信技能也不执行了，还需要进程隔离吗？
需要。LLM 修补时会读网页和工具输出，这是一条不经过签名的注入路径。而且死循环不需要恶意，一次写错就能挂掉整个服务。
process 档挡不住读文件和联网，宣传"隔离"会给人错误的安全感。
成立。所以文档和日志只说它保护密钥、权限、可用性，并给出逐项表格。需要文件和网络隔离的部署，必须选 sandbox 档，它在不支持的平台上拒绝启动。
每次执行都要起进程、跨进程传数据，会拖慢热路径。
冷启动在预热池里完成，热路径只剩 JSON 往返。和一次 LLM 调用比，这点开销可以忽略。具体数字在第二阶段实测，验收标准见下文；不达标就调大池或重新评估。
用 fork server 可以把启动成本降得更低。
fork 出来的进程带着宿主内存，包括 API Key。除非 fork server 本身从一个干净的 spawn 进程派生，而这又回到了预热池的复杂度。第一期不做。
宿主驱动步骤循环，等于把编排逻辑拆到了两个进程，调试更难。
编排逻辑全部在宿主，worker 只是"执行一个函数并回报"，反而比现在的单体 execute_script 简单。inprocess 档和 process 档共享同一套编排代码，可以用同一组测试覆盖。

分阶段实施

P1

抽出 Runner 接口，行为不变（已完成）

把 execute_script 拆成编排和 InProcessRunner；StepContext 的宿主逻辑移到 CtxBridge；把沙箱代码抽到纯标准库模块；给 verify 加超时；guard 遇到未注册工具时拒绝。

验收：现有 93 个测试不改一行即通过。

P2

ProcessRunner

实现 worker 文件、JSON 帧协议、预热池、超时击杀、环境清理、rlimit 和 Windows Job Object、每次执行的预算，以及 run_tests 的并发限制。默认值切换为 process。

验收：全部测试在 process 档下通过；逃逸语料库在 worker 内拿不到宿主环境变量；死循环在超时后 1 秒内被终止；预热池命中时，单次执行的额外开销 p50 < 10 ms（Linux）。

状态：已实现。Windows 上实测：预热池命中时，一个两步、一次工具调用的脚本额外开销 p50 约 3.7 ms，冷启动约 220 ms。POSIX 上的 rlimit 只做了替身测试，还没有在真实 Linux 上运行过。预算默认值定为工具 500 次、ctx.llm 100 次。无法启动 worker 时抛 WorkerStartError，不当作脚本错误去修补。

P3

SandboxRunner（Linux）

实现 Landlock 和 seccomp，不可用时拒绝启动。规定 untrusted_shared="shadow" 必须配合 sandbox 档。在 Docker 镜像里验证。

验收：在 worker 内读 /etc/passwd、建立 socket、执行 execve 都失败；内核不支持时给出明确错误，不降级。

状态：已在 Debian 13（内核 6.12，x86_64，Landlock ABI 6，非 root 用户）上验证：读 /etc/passwd、写 /tmp、建立 socket、fork、执行程序、给父进程发信号都被拒绝；线程、标准库读取、ZoneInfo 正常；系统调用号与内核头文件逐个核对一致（x86_64 共 48 个，aarch64 共 44 个）；默认档位改成 sandbox 后全量测试全部通过。验证中发现并修复了一个问题：Linux 上的事件循环在创建时要建一对 socket，必须在进入 sandbox 之前创建。aarch64 上的真实运行和 Docker 内的行为仍待验证。

原计划：代码已完成，待在 Linux 上验证。实现在 skills/_confine.py：Landlock 只读放行 Python 安装目录、sys.path 和时区数据，不允许写任何地方；seccomp 用手写 BPF 过滤器，不加依赖，支持 x86_64 和 aarch64。过滤器禁止 socket、execve、创建进程（只允许带 CLONE_THREAD 的 clone）、ptrace、io_uring 等调用，发信号只能发给自己。过滤器逻辑在所有平台上用 BPF 解释器逐条验证过；真实的内核约束和系统调用号核对，只在 Linux 上运行。

P4

自动上线前的变更审查

修补或提炼出的新版本如果新增了 import、工具或子技能调用，或者用到了 ctx.llm 的新调用点，不自动上线，转为等待人工确认。这是止血补丁里留下的另一项。

验收：只改动逻辑的修补照常自动上线；扩大能力的修补进入待审状态，可以通过 API 和 CLI 批准。

验证

  • 逃逸语料库：把 tests/test_sandbox.py 里的逃逸样例，加上"假设已逃逸"的直接原语（读 os.environ、开 socket、fork、分配 2 GB 内存），对每一档跑一遍，断言结果与隔离级别表一致。
  • 故障注入：worker 中途崩溃、发送畸形帧或超大帧、不回复、在 ask_user 等待期间被杀。宿主都要给出确定的失败结果，并且不残留进程。
